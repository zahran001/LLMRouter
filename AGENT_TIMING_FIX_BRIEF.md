# Coding Agent Brief — Precise Mock Timing (Busy-Wait Fix) + Eval Rigor

## Background
The Week 1 metrics pipeline is correct. The 2 failing tests (fast config, 100ms TTFT)
were traced to `asyncio.sleep()` overshooting its target by ~25-40ms on Windows — a
systematic BIAS, not random noise. The pipeline faithfully measures the mock; the mock
just doesn't deliver the timing it was configured for.

Decision: **fix the mock's timing precision** (Option B), so the mock's delivered
timing matches its configured target. This keeps ground truth = configured value
(clean, reproducible across machines) and makes the mock a more faithful vLLM stand-in
(real GPU token timing is precise, not sloppy). Do NOT widen tolerances to paper over
the bias.

---

## Part 1 — The busy-wait / hybrid sleep fix

### The technique
Replace the mock's raw `await asyncio.sleep(target)` with a **hybrid sleep**: sleep
most of the interval cheaply, then spin-wait the final slice against a monotonic clock
for precision.

```python
import asyncio, time

# Tunable: how much of the tail to spin-wait. Start ~5ms; [CALIBRATE] on the target machine.
SPIN_MARGIN_S = 0.005

async def precise_sleep(duration_s: float, spin_margin_s: float = SPIN_MARGIN_S):
    """Sleep `duration_s` with sub-ms accuracy.
    Coarse asyncio.sleep for the bulk, tight spin for the final margin.
    Yields to the event loop during the spin so we don't starve other streams."""
    if duration_s <= 0:
        return
    deadline = time.perf_counter() + duration_s
    coarse = duration_s - spin_margin_s
    if coarse > 0:
        await asyncio.sleep(coarse)
    # Spin the remainder, yielding control so concurrent streams still progress.
    while time.perf_counter() < deadline:
        await asyncio.sleep(0)   # 0 = yield to loop without a real timer wait
```

### Requirements
- Use `time.perf_counter()` (monotonic) for the deadline, never wall-clock.
- The spin loop MUST `await asyncio.sleep(0)` each iteration (yield to the loop), so
  serving multiple concurrent mock streams doesn't block. A pure `while` with no await
  would starve the event loop — do not do that.
- Apply `precise_sleep` to BOTH the `ttft_ms` wait and the `tpot_ms` inter-chunk gaps.
- `SPIN_MARGIN_S` is `[CALIBRATE]`: 5ms is a starting guess. It must exceed the OS's
  `asyncio.sleep` overshoot so the coarse sleep never blows past the deadline. Measure
  the actual overshoot (see Part 2) and set the margin just above it.
- Keep the high-variance config's injected tail working: the tail delay is a LARGER
  precise_sleep, not a return to raw sleep. Precision applies to the base timing; the
  deliberate tail spikes are still precise, just larger.

### Do not
- Do not spin without yielding (event-loop starvation).
- Do not set a huge spin margin (e.g. 50ms) — that burns CPU for the whole margin on
  every chunk. Margin should be just above measured overshoot.
- Do not touch the metrics/parser/consumer code. This is a mock-only change.

## Part 2 — Prove the fix worked (timing self-test)

Before re-running the full suite, add a direct measurement test of the mock's timing
accuracy, independent of the metrics pipeline. This isolates "is the mock precise?"
from "does the pipeline measure correctly?" — two separate claims that must not be
conflated.

`test_mock_timing_accuracy`:
- Drive the mock directly (no router, minimal parsing overhead), capture raw chunk
  arrival times with `perf_counter()`.
- For each stable config (fast/slow/bursty), assert the mock's DELIVERED median TTFT
  and TPOT are within a TIGHT band (e.g. ±5ms) of the configured target.
- This is a stricter gate than the pipeline eval and tests a different thing: mock
  fidelity, not pipeline correctness. Keep it separate.
- Record the observed overshoot/undershoot so the spin margin can be tuned.

## Part 3 — Eval rigor requirements (the important part)

The eval is only trustworthy if it fails when it should. Ensure ALL of the following
hold after the fix. These are the properties that make the eval rigorous rather than
merely green.

### 3a. Separation of concerns — one claim per test
Each test asserts exactly ONE thing, so a failure localizes the cause:
- Mock timing accuracy (Part 2) — is the mock faithful to its config?
- Pipeline correctness (Tier 3) — does the pipeline measure the mock correctly?
- Percentile math (Tier 1) — is the percentile fn right, in isolation?
A test that would pass/fail for two different reasons is not rigorous — split it.

### 3b. Independent ground truth
Percentile expectations remain hard-coded from an independent source (numpy pinned
method or hand calculation), never generated by the function under test. Re-confirm
this survived the changes.

### 3c. The negative controls must still bite
Re-run both negative controls (broken percentile → returns mean; TTFT→TPOT leak) and
confirm they STILL FAIL when the bug is injected. A fix that accidentally loosens a
tolerance can silently defang a negative control. If a negative control stops failing,
the eval has lost teeth — treat that as a build-breaking regression.

### 3d. Tolerance provenance — no magic numbers
Every tolerance constant must trace to a documented source:
- The hybrid band `max(±15ms, ±10%)` — from the spec.
- The 15ms floor — `[CALIBRATE]` from the 200-run noise measurement.
- The spin margin — `[CALIBRATE]` from the measured overshoot.
- The high-variance p99 multiplier — `[CALIBRATE]`.
No constant should exist that someone can't trace to either the spec or a calibration
run. A number chosen to "make the test pass" is a rigor failure — flag any you find.

### 3e. Determinism check
Run the full deterministic eval (Tier 1 + Tier 3) 5 times in a row. It must pass all
5 with no flakes. A test that passes 4/5 is not deterministic — either the tolerance
is too tight for real jitter (calibrate) or there's an ordering/seed bug (fix).
Report the pass rate.

### 3f. The high-variance config still separates
After the timing fix, re-confirm the high-variance eval still shows p99 > p95 > p50
with p99 meaningfully elevated. The precision fix must not accidentally flatten the
injected tail (e.g. if the spin margin swallowed the tail spikes). This config is the
only guard on the tail math — verify it survived.
